# MVP release checklist (v0.1.0)

This checklist maps the design acceptance criteria to their verification. Run
`nix develop -c npm test`, `nix develop -c npm run typecheck`, and
`nix flake check` on the release commit before tagging.

## Mail server

The full mapping lives in
[mail server acceptance test map](../design/mail-server-acceptance.md). Summary:

- [x] Generated local parts are readable, unique, policy-free word combinations.
- [x] Changing policy never changes an alias address.
- [x] Alias list filtering and sorting are deterministic.
- [x] Unknown and disabled recipients are rejected before acceptance; expired
      recipients are accepted and quarantined.
- [x] Policy or database failure returns a temporary failure, never "unknown".
- [x] Mail to an active alias reaches the inbox.
- [x] Inbound messages never extend the lease.
- [x] Mail arriving at or after expiry is quarantined.
- [x] Outbound mail renews an active alias when `renew_on_outbound` is true.
- [x] Sending through an expired alias reactivates it only when
      `renew_on_outbound` is true.
- [x] A spoofed inbound `MAIL FROM` cannot trigger renewal.
- [x] Client-supplied `X-Wickmail-*` headers are stripped and cannot route.
- [x] Disabled aliases neither receive nor send mail.
- [x] Recovery and retention are idempotent and crash-safe; reconciliation
      repairs either store.
- [x] Reply provenance defaults to the single receiving alias and prompts on
      multiple aliases.
- [x] Outbound replies use the alias as envelope sender and sole `From`, and are
      DKIM-aligned.
- [x] Recovering a quarantined message does not duplicate it.
- [x] No accepted message is permanently rejected or bounced for alias policy.

## Web management app

- [x] A user can generate and copy a readable seven-day alias in under a minute.
- [x] No field chooses the local part and policy is never derived from the
      address.
- [x] Aliases can be filtered by state and expiry and sorted by expiry, recently
      used, or recently created.
- [x] No-expiry and never-used aliases have deterministic sort positions.
- [x] Renewing and copying an existing alias takes two primary actions.
- [x] Labels and purposes are editable; lease policy can change; aliases can be
      disabled and re-enabled.
- [x] Active, expired, and disabled states are visually unambiguous.
- [x] The interface explains that inbound mail does not renew an alias.
- [x] A reply to a one-alias message defaults to that alias; multiple aliases
      require an explicit choice; a primary-only message uses the primary
      identity.
- [x] The composer reports queued, rejected, and identity-error outcomes.
- [x] Quarantined mail can be recovered without an IMAP client.
- [x] Core flows work on phone-sized and desktop browsers.

Verified by `apps/web/test/*` and `apps/server/test/api-*.test.ts`.

## Android shell

- [x] All web management flows work inside the Android app without a separate
      mobile implementation.
- [x] Reply-as-alias and multiple-alias prompts work inside the WebView.
- [x] The native shell does not evaluate leases or select reply identities.
- [x] External links cannot navigate the management WebView to arbitrary
      origins.
- [x] Back navigation, session expiry, rotation, and process recreation behave
      predictably.
- [x] Alias copy and share actions work on supported Android versions.
- [x] Release builds expose no WebView debugging or credential-bearing bridge.
- [x] Offline behavior cannot falsely report successful alias creation, renewal,
      or recovery.

Verified by `apps/android/app/src/test/**`.

## Operational hardening

- [x] Mail store, SQLite database, and configuration are backed up; restore and
      reconciliation are exercised by an automated drill
      ([backup](operations/backup.md)).
- [x] Monitoring covers SMTP queue depth, spool depth and age, disk usage,
      certificate expiry, authentication failures, policy-service failures, and
      reconciliation results ([monitoring](operations/monitoring.md)).
- [x] SPF, DKIM, DMARC, reverse DNS, and TLS records and a verification script
      exist ([deliverability](operations/deliverability.md)). External
      test-account placement is an operator step.
- [x] A Nix-based deployment and upgrade guide exists
      ([deployment](operations/deployment.md)).
- [x] Abuse controls are verified by automated tests and documented
      production-like steps ([abuse verification](operations/abuse-verification.md)).
- [x] Release notes and known limitations are written
      ([release notes](v0.1.0-notes.md)).

## Release steps

1. Ensure `main` is green: `nix flake check`, `nix develop -c npm test`,
   `nix develop -c npm run typecheck`.
2. Confirm the [known limitations](v0.1.0-notes.md) are accurate.
3. Tag the release on `main` (maintainer only; see the release notes).
